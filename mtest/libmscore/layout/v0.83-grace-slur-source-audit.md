## Horizontal admission and slur geometry are separate

Evolution's commonItemContext4 rejects a matching slur endpoint, including a
same-track/tick match, before the optional pair policy runs. Grace chords and
their parent share musical onset time, so this guard can reject the whole group
when a slur is added. buildGraceBeforePlan4 then fails, live grace placement
retains native packing, and prepareGraces4 rejects the full system plan.

Do not remove the score-wide slur guard. First add a narrowly validated allowance
for an ordinary before-grace-to-own-main slur, with explicit resolved endpoints,
member ownership/order, same staff/voice, unedited automatic geometry and no
other attachments. Preserve all unrelated spanner/line-attachment rejection.
The first allowance should preserve the newly accepted horizontal note layout
while still using Evolution's existing slur drawing. It is not a curve port.

Studio computeNotePadding's named line-attachment length floors cover ties,
glissandi, bends and note lines. That is not evidence for borrowing minTieLength
as a grace-slur spacing rule. Check the bounded slur's attachment inputs rather
than treating all spanners as equivalent.

## Endpoint coordinates: parent translation already exists

Evolution Slur::slurPos and Studio SlurTieLayout::slurPos both construct endpoint
positions from chord + segment + measure, and add the grace chord's parent
position for a grace endpoint. The ordinary path therefore does not have an
obvious missing-parent-translation fix. Keep coordinate transforms explicit;
do not add another parent position or compensate with a horizontal constant.

Anchor selection and clearances do differ. Studio selects stem-side anchors
using beam-aware endpoint helpers, has hook-specific handling and scales some
stem-side offsets by intrinsic chord magnification with a minimum offset.
Evolution's older stem-anchor condition generally requires both endpoints to
be unbeamed, with a separate hook exception and older fixed offsets. A global
constant substitution would change unrelated ordinary slurs and is not justified.

## Important collision-model difference for grace groups

Evolution SlurSegment::layoutSegment skips the entire start and end segments
when checking collision geometry. In a before-grace-to-own-main slur these are
the same musical segment, containing all the grace notes and the main chord.
That skip therefore also removes intermediate grace notes/accidentals from
this collision correction. The initially chosen Bezier curve can remain even
when sibling grace components would warrant a different contour.

Studio getSegmentShapes iterates the endpoint segments inclusively, then
getSegmentShape removes selected items by identity, endpoint role, visibility,
voice and type. It does not simply discard both endpoint segments. Intermediate
grace components can remain collision obstacles. addMinClearanceToShapes adds
type-specific clearance; avoidCollisions adjusts endpoints/control points with
bounded iteration (MAX_ITER 30) and shape constraints. computeBezier also calls
endpoint adjustment before its collision process. This is a substantive model
difference, not just slurMinDistance or one shoulder-height default.

Direction selection is another independent policy. Studio retains an exception
for a grace start ending on its own parent, but can consider mixed directions
for a grace start ending elsewhere; it also scans multiple-voice context.
Evolution has older direction-mixture/voice/tie rules, and its layoutSystem and
layout paths are not identical for long slurs. Keep initial controls confined
to same-parent, single-system grace slurs so a direction-policy port does not
silently enter the horizontal-spacing change.
