# v0.43: Studio 4.7.5 horizontal-spacing source audit

Date: October 23, 2026. Evolution checkpoint audited: `e62a383` (v0.42).
This checkpoint changes documentation only. The user reports v0.42 tests passing.

## Result and scope

The remaining work is a port of a connected horizontal-spacing pipeline, not
another adjustment to the spring formula. Studio's duration weights and spring
solver have already been adapted, but most of its collision policy and the
placement pass that feeds that solver have not. Evolution still determines
initial segment positions and most collision floors using its own algorithms.

Audit the complete HorizontalSpacing implementation and header, its system
collection/finalization callers, padding-table construction, shape data model,
segment shape construction, and selected chord/note geometry producers. Trace
measure preparation and shape/tick ordering at their spacing interfaces. This is
not a full audit of every element renderer, accidental-column algorithm, vertical
autoplace routine, or every use of horizontal distance elsewhere in Studio.
Those producers remain explicit dependencies rather than implied parity claims.

No additional visual test score is needed for this documentation checkpoint.
Screenshots validate integration; they should not be the primary means of
discovering upstream rules. The latest H27-H35 images support the improved
distribution but do not establish exact coordinate parity.

## Actual call and data flow

1. Measure preparation lays out noteheads, rests, non-cross beams and annotations,
   builds segment shapes, then computes segment durations. Studio's
   MeasureLayout explicitly computes ticks after shape visibility is established.
   Grace-note groups and system header/trailer changes can update these inputs.
2. During SystemLayout::collectSystem, adding a measure calls
   updateSpacingForLastAddedMeasure. It can reconsider the preceding measure and
   the newly added one together, with earlier positions serving as a boundary.
   Its result participates in deciding whether a measure fits on this system.
3. Once the system is collected, Studio hides empty staves, rebuilds segment
   shapes, updates decorations, end barlines and trailers, then calls
   computeSpacingForFullSystem. HBoxes divide the system into measure groups.
4. spaceMeasureGroup flattens each group's segments into one coordinate stream.
   spaceSegments places against preceding segments and supplies natural rhythmic
   advances. Later passes adjust right-aligned items and edge constraints before
   setPositionsAndWidths derives segment and measure widths from the positions.
   Minimum measure widths are enforced with springs, moving following measures.
5. An overfull system is recomputed with reduced duration stretch and padding.
   A remaining impossible fit can finally reduce chord/rest widths enough to
   allow collisions. A system that needs filling shares one spring force across
   its rhythmic segments. Only then does system element layout/staff spacing
   continue. This is several related passes, not one fixed count for every score.

Evolution's Score::collectSystem still calls Measure::computeMinWidth on each
candidate and sums the measure widths to make its fitting decision. Its final
system stage updates barlines/trailers and applies our optional pooled spring
targets. That last change cannot substitute for steps 2-4 above.

## What is already adapted, and its exact boundary

| Area | Current implementation | Remaining boundary |
| --- | --- | --- |
| Duration law | spacing4DurationStretch and segmentSpacingStretch4; 3.5sp quarter reference; clamped user stretch applied once | Small-note scaling, density and MMRest duration policy absent; shortest-duration visibility adapted to Evolution API |
| Springs | spacing4SpringForce; flexible width excludes signed offset; collision pre-tension retained | Solver parity does not imply input-floor parity |
| System justification | systemSpacingWidths4 pools eligible ordinary systems | Entire system falls back for frames, MMRest, timed non-CR springs, minimum-width slack or invalid values; single-measure path retained |
| Final-system fill | Optional terminal/section fill decision, including frame lookahead | Still uses Evolution's measured natural width and system collection |
| Cross-beam corrections | Bounded single-stream ordinary/secondary-beam cases, sustained-voice allowance, beamlet clearance | Not Studio's general multivoice classifier, same-direction stem checks, nonadjacent stem checks or general kerning |
| Cross-staff kerning | Supported negative-offset pair can omit blanket notehead-width floor | Actual collision test and most padding remain Evolution's |
| Geometry | Native Evolution chord/note/segment shapes | Studio's producers, tagged items, beamlet shapes and grace-group representation are not wholesale ported |

Both spacingLayout4 and beamLayout4 remain independently selectable. A future
spacing path must continue to work with either beam option, not assume that
Studio beam geometry is always available.

## Structural gaps and implementation implications

### A. Collision inputs lose musical identity

Evolution's ShapeElement is a QRectF plus an optional debug name. Studio retains
an EngravingItem pointer per rectangle. Studio's distance loop uses that item to
select asymmetric type-pair padding, magnification, same-voice restrictions,
kerning limits, accidental clearance, lyric behavior and line attachments.

Evolution's Shape::minHorizontalDistance tests rectangle intersection; its
Segment::minHorizontalDistance adds broad spacing rules afterward. These are not
equivalent to Studio's per-pair policy. A rectangle debug name cannot recover
the source note's voice, staff, actual duration or spanner attachments.

Recommended adapter: temporary, spacing-only tagged rectangles built from
Evolution elements and their geometry, scoped to one spacing pass. Keep the
global Shape/skyline behavior intact. Tag noteheads, accidentals, dots, ledger
lines, stems, hooks, rests, barlines and header items individually. An entire
chord cannot be tagged as NOTE: that would misclassify its accidentals and stems.
Synthetic barriers and horizontal-only spacers need explicit treatment too.
Preserve identity and coordinates through translation/copy; do not cache element
pointers across structural edits. Unknown geometry must be accounted for through
a documented fallback, never silently omitted.

This is an implementation recommendation, not an upstream data structure we
already have. First establish geometry coverage against native shapes before
switching collision policy. Merely adding a pointer field without updating shape
producers would leave the important rectangles untagged.

### B. Placement and barlines are coupled across measures

Studio's spaceAgainstPreviousSegments can move already placed onsets to spread
collision clearance over intervening rhythmic segments. It uses system
coordinates and checks across a measure boundary. Its stopping rules consider
duration overlap, lyrics/harmony and preceding measures. Evolution has a related
lookback redistribution, but it stops at this measure's first enabled segment
and uses its older colliding-distance function.

Studio derives widths after positioning, including rules for leading clefs,
keys, time signatures, repeats and right-aligned segments. Copying just the
lookback loop into Measure::computeMinWidth would still leave incompatible
measure-boundary bookkeeping. Port the position stream and width reconstruction
together behind the option.

### C. Minimum width is an actual spacing pass

Evolution can clamp a measure's bounding width without distributing that slack
over its segment floors. v0.42 deliberately rejects that system for pooling.
Studio computes a minimum based on available system width, shortened measure
duration and header/first-accidental position, then distributes the deficit
through springs. Adopt this with position reconstruction; do not simply remove
the v0.42 slack guard. Pickups and narrow systems need explicit coverage.

### D. System fitting needs the new natural-width calculation

Studio recalculates neighboring measures during collection and the whole system
after hidden staves and courtesies change. Its squeeze loop reduces duration
stretch by 0.33 steps and shape padding by 0.2 steps; only after those attempts
does it allow further collision-producing width reduction. These settings belong
in a pass context, not persisted modifications to the score's styles.

Port final-system recomputation before fitting integration. Then use the same
natural-width engine while collecting measures; otherwise the line breaker is
still deciding with different widths from those it ultimately lays out.

### E. Geometry readiness is part of the algorithm

Evolution's Chord::shape explicitly omits cross-staff stems because their final
direction/length is not ready. Studio includes stem geometry and supplements it
with cross-staff stem checks that can treat a stem as effectively infinite in
height before staff distances are known. Its chord shape also includes beamlets.
Do not enable Evolution cross-staff stem rectangles indiscriminately or use final
staff distances as a prerequisite for initial spacing; either can introduce a
circular dependency or stale geometry.

Evolution's earlier getNextMeasure preparation computes ticks before final shape
creation. Our experimental computeMinWidth already recomputes ticks later, so
this ordering difference alone is not evidence of a current regression. The new
path must explicitly rebuild relevant shapes/visibility before computing its
duration inputs, including repeat layouts and hidden-staff changes.

### F. Equal style names do not establish equal effective inputs

Studio has spacingDensity, cue-note rhythmic scaling and additional MMRest width
styles that this port currently lacks. Existing Evolution style import code
skips several of those fields. Existing common-style defaults also differ
(for example minMeasureWidth 5sp versus Studio 8sp, minNoteDistance .2sp versus
.35sp). Keep legacy defaults; read shared styles from the score and state any
new experimental defaults explicitly. Matched fixtures isolate policy changes;
general score comparisons also need effective-style and font checks.

The existing duration routine uses prev(ChordRest) within the measure, matching
the upstream call. Do not change this to a cross-measure predecessor merely
because the placement stream will span measures.

with more screenshot-driven constants or change accidental-column layout without
separate evidence that it is the responsible producer. Packaging, source build
lists, C++11 and Qt 5.9.9 compatibility belong in that implementation stage.

## Verification strategy

Keep the existing visual scores H1-H35; issue new numbered fixtures only for
new behavior that those controls cannot exercise. New applicable inputs must
save spacingLayout4 enabled. Keep explicit off/on/off and repeated-layout checks
in automated tests; retain both beam styles for coupled spacing cases.

Use source-level comparisons for pure policy with real adapter data where
possible. Mocked-policy harnesses isolate arithmetic but cannot establish that
native geometry, visibility, staff scale and layout timing match Studio.
Integration checks should report the first diverging stage: input shapes/styles,
natural segment positions, reconstructed measure widths, collected system
membership, then final justified positions. Normalize visual comparisons in
spatium units rather than screenshot pixel width or application zoom.

At each code milestone, record files changed, the restored checkpoint, actual
checks run and remaining fallbacks. Full application/mtests are unavailable in
this workspace; the user's passing v0.42 run is integration evidence for that
checkpoint only. This documentation-only audit needs no application test rerun.

Open follow-up producer audits: accidental columns and grace-group placement;
new/unsupported spanner attachment APIs; complete annotation and visibility
semantics; performance of cross-measure lookback on full scores. These do not
prevent starting the common-notation adapter, but prevent claiming a complete
Studio engraving-engine port.
