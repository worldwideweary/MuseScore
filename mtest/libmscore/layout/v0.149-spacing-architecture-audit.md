# v0.149: spacing architecture audit and consolidation decision

Date: October 25, 2026. Audited Evolution code: delivered v0.148 38213f2,
plus documentation-only native-result commit 15792f5. No engraving changes
in this audit. v0.148 native mtests and its requested visual sequence pass.

## Decision

Keep the duration/spring arithmetic, typed pair-distance kernel, position
stream/width reconstruction, accepted beam work and regression fixtures.
Replace the surrounding eligibility/provenance/preparation integration in
coherent stages. Stop adding slur-member/measure-count contracts as the way
to extend ordinary horizontal spacing. Do not discard the whole port, and
do not claim that deleting its guards would produce a complete port.

The main architectural defect is a partially transactional system planner
embedded in a nontransactional preparation/distribution pipeline. A fresh
plan is usually committed only on success, but the style has already changed
rhythmic weights, measure stretch and some grace positions before that plan
is accepted. A rejected plan can still enter modern pooled justification.
Calling that result "legacy layout" was incomplete: it can be a hybrid of
modern rhythm/local packing and native collision/fitting rules.

This is separate from the v0.147 performance shortcut: rejecting that shortcut
runs normal affected-range layout, which can still accept the modern planner.
The shortcut does not resolve the general lifecycle/coverage problem.

but extending isolated eligibility scopes did not complete those architectural
requirements. Repeating an inventory without changing that approach would not
be a useful next step.

## Boundary register: keep, replace or complete

| Gate family | Valid reason for retaining a guard now | Required architectural treatment |
| --- | --- | --- |
| Finite values, valid durations/ownership, exact provenance, beam convergence | Prevent invalid geometry, dangling identity and unsolved circular preparation | Keep invariants; give failures stage/object identity; never silently omit items |
| First grace member, one/two specialized slurs, selected exact musical pair | Protect specialized curve anchors/obstacles; currently also gate horizontal inputs | Keep curve bounds local to the curve fitter; replace horizontal whitelist with general endpoint metadata |
| Explicit direction/AUTO agreement, same-measure main-start restriction | Current adapter lacks authoritative prepared direction/attachment data | Prepare resolved direction once; apply source-derived endpoint policy generally; do not demand renderer/source equality as permanent admission policy |
| Missing page/system coordinates during a pair query | Current implementation uses pagePos too early | Express pair comparisons in one prepared staff/segment frame; keep cross-staff coordinate dependencies explicit |
| Unknown/shared/legacy aggregate shape ownership | Rectangle matching cannot establish missing producer identity | Emit identity at producers into spacing-only snapshots; preserve old Shape API/legacy behavior; retain coverage comparisons as validation |
| Articulations, ties/note spanners, lyrics/harmony and other annotations | Their collision/attachment policies and sometimes producer identity are not ported | Port general per-item policies and line/annotation metadata; avoid per-score endpoint exceptions |
| Hidden staves, frames/MMRests, cue/measure rests, manual leading space | Current group stream and style inputs do not model these source cases | Complete container, visibility and effective-style mapping in the shared engine |
| General cross-staff/cross-beam/tremolo interactions | Stem side/length and staff distance can form real dependencies | Use prepared cross-staff constraints/phase ordering; replace bounded voice/group-count assumptions after those inputs exist |
| Strong compression | Only first three positive-duration squeeze passes are adapted | Port full source squeeze/reduction policy deliberately; report collision-permitting stage separately |
| One-system/one-page/one-two-staff end-anchor shortcut | Reusing positions requires proof of unchanged geometry and pagination | Keep conservative shortcut guards; do not confuse their rejection with spacing-style rejection; ultimately share the ordinary dirty-range pipeline |

Beam/tremolo DRAWING coverage does not imply horizontal-spacing coverage:
buildSpacingPlan4 currently rejects every chord carrying a tremolo. Likewise,
backported time-signature or chord-bracket drawing elsewhere does not implement
HorizontalSpacing's corresponding edge/padding stages in this checkout.

## Recommended engine boundary

Use one explicit spacing input context and one publication decision for each
measure group/system. Feed the same prepared inputs to collection, final natural
spacing, justification and compression. Preserve the existing option-off path.

1. Native preparation produces current note/rest/header geometry and resolved
   attachment data. Emit spacing-only tagged rectangles directly where the
   native producer knows their owner, rather than recovering identity by equal
   rectangles. Keep every contributing obstacle; unsupported inputs must be
   named, not dropped. Snapshot lifetime ends before any preparation mutation.
2. Build an immutable input view: visible-staff map, segment timing, musical
   order of grace members, per-item padding/kerning metadata, line endpoints,
   magnification and effective styles. Index slur endpoints once per preparation
   pass rather than scanning all score slurs in repeated pair queries.
3. Solve the source-derived position stream and width reconstruction from that
   view. Reuse the current arithmetic and pair-distance core where equivalent.
   A slur's specialized curve eligibility must not decide whether note shapes
   can participate in this general stream.
4. Collection and final fitting consume that same solver. Incremental extension
   uses a documented stable prefix and the affected neighboring groups, as in
   upstream updateSpacingForLastAddedMeasure, rather than repeatedly rebuilding
   every earlier grace projection. Invalidate by actual producer dependencies.
5. Publish a coherent result only after the requested policy succeeds. During
   transition, represent engine selection and rejection stage explicitly. If a
   full legacy fallback is still needed, recompute a genuinely legacy-consistent
   result; merely rejecting the final plan is insufficient while modern rhythm
   and local packing remain active. Avoid a global temporary style toggle,
   which would also affect unrelated callbacks and engraving decisions.
6. Rebuild dependent curves/skylines/staff distances/page placement through the
   native pipeline. For unchanging horizontal input, reuse the prepared result
   through a general update classification; preserve one-key/one-undo semantics.

Direct emission still requires item-type mappings: that is necessary data-model
adaptation, not a whitelist of combinations such as first grace plus one slur.
A generic rectangle alone cannot reproduce tie length, lyric melisma or voice-
aware kerning. The plan is to port those inputs and policies, not to pretend
that all missing rules disappear behind a common interface.

For automatic slurs, spacing flags must describe the direction actually used
by the renderer. Prepare a single direction result consistently for both
consumers. If retaining native direction temporarily, record that producer
parity limitation explicitly while keeping valid geometry in the modern engine.
Do not silently substitute 4.x direction flags against an oppositely rendered
curve, and do not keep the current equality proof as a permanent feature gate.

## Finite work packages and acceptance gates

These are six architectural milestones, NOT a promise of six patches. Each
may have several independently recoverable commits. No patch-count, hour or
percentage-complete estimate is justified by the present native evidence.

| Package | Deliverable | Acceptance gate before broadening work |
| --- | --- | --- |
| A: prepared geometry and attachment inputs | A spacing-only producer/context layer; resolved slur endpoints/direction, grace member order and per-item metadata; retire horizontal dependence on specialized curve contracts | Existing curve-specific bounds stay intact; every native rectangle is accounted for; all valid start/end grace members and ordinary slur directions remain in the modern engine; unsupported items have object/stage diagnostics |
| B: one collection/publication lifecycle | One engine context shared by provisional collection and final group fitting; explicit engine outcome; replace full-prefix rebuilding and hybrid fallthrough | Natural/justified/squeezed outcomes use consistent inputs; adding/removing/reanchoring attachments does not silently switch algorithms; full/range/undo/reload converge; rejected work leaves a coherent documented outcome |
| C: containers, effective styles and item policies | HBox groups, visibility/hidden staves, cue/MMRest/measure-rest duration/geometry, leading offsets, right alignment, lyric/harmony margins, tie/line lengths and remaining supported item dispatch | Source-derived stage comparisons for each policy family; unknown shapes never vanish; ordinary valid 3.x scores do not need first-member/count whitelists |
| D: cross-staff/cross-beam/tremolo spacing | General source constraints with prepared stem sides/lengths and independent voices; complete squeeze stages | Adjacent/nonadjacent stems, sustained/independent voices, beamed rests and tremolo spacing use common mechanism; both beam option states work; staff-distance iteration stabilizes |
| E: general edit invalidation and efficiency | Dependency-based update boundaries for offsets, start/end reanchors, notes/styles, undo/redo and system/page changes | Debug responsiveness measured with the same score/actions; no curve/beam/spacing jumps; unchanged horizontal input avoids recollection without timers/key batching; modified input updates the required range |
| F: completion audit and compatibility corpus | Reconcile all 54 source functions and retained limitations; run representative complete scores plus focused regression families | Option off matches untouched Evolution behavior; option on has no unexpected normal-notation fallback; deterministic load/edit/undo/redo/export; measured correctness/performance limits published |

A and B are the immediate priority and should be developed together at their
interface. C and D finish missing policy/dependency families; E generalizes
performance once the normal pipeline is coherent. Current offset optimizations
remain useful during this transition and should not be removed merely to make
the design look cleaner.

First implementation stage after this audit: prototype the prepared attachment
and tagged-geometry seam on an isolated branch/commit, demonstrate start-anchor
traversal without consulting specialized curve helpers, and prove input/legacy
coverage before switching runtime selection. Do not ship another member-specific
fix. Then integrate that seam with an explicit preparation/publication context.
Use the prototype to refine the remaining effort estimate; no further long
sequence of user builds should be presented as "just a few corner cases."

Target scope must be honest: general pitched notation and features representable
in this Evolution checkout. Tablature remains the user's deferred last priority.
Studio-only element types absent from this branch need explicit mappings or a
stated exclusion, not implied parity. Accidental-column and general slur-curve
producer parity remain separate from the horizontal solver itself; record
those differences when attributing visual discrepancies.

## Verification and how to reduce the user's test burden

Retain the existing H/R/T/grace/slur scores as a regression corpus. Test
mechanisms and state transitions, not every Cartesian combination on every
patch. Keep full combination checks for small kernels and representative
pairwise integration cases for expensive layout. Avoid tests that merely
repeat current eligibility restrictions as if those restrictions were goals.

Add stage-level comparison data: prepared item identity and staff coordinates,
resolved attachment flags, natural positions, group widths, system membership,
justification/compression parameters, published positions, then vertical/curve
geometry. Report the first divergence. Current timing counters report calls
and durations but cannot say whether a plan was accepted; do not infer engine
switches from plan call counts or screenshot differences alone.

The user should run native tests at coherent implementation milestones and
visually review a small named acceptance pack. Do not request a new screenshot
for every guard extension. Tests must cover both independent style switches,
manual offsets/leading space, all valid anchor members, start/end movement,
undo/redo, forced/natural breaks and repeat-layout determinism. Performance
runs need matched score, Debug flags, edit direction and engine outcome.
Current logs contain no Studio command timings; there is no numerical Studio
speed baseline, and the v0.147 shortcut has not been observed in those logs.
