## Why reanchoring can still be slow

Shift+Arrow changes anchors/ticks/possibly tracks through changeAnchor and
normal undo operations. Those changes dirty a musical range. The current
update recollects systems, prepares grace/beam geometry, tries spacing plans
for successive fitting prefixes and computes final placement. A pure offset
shortcut cannot be applied blindly because the new endpoint can change the
note-kerning side exceptions and therefore horizontal spacing.

This stage removes the shown spacing-mode switch; it does not skip that
range-layout pipeline or claim improved command timing. Newly admitted spans
now receive the modern solve consistently, so responsiveness must be evaluated
separately from elimination of fallback.

## Native result and correction

The user reports tst_spacing failing and supplies result(20261025-044137).xml.
All eight slurAnchorTraversal4 rows fail pointer comparisons; the separate
slurAnchorSpacing4 and slurOffsetLayout4 cases pass. The test's expected list
incorrectly contains only main chords. Native nextChordRest/prevChordRest
(default skipGrace=false) visit before/after graces, so after reaching the
next owner's main chord the next stop is its first after-grace, not its next
main chord. This was an incorrect test assumption, not a reason to change
Evolution's navigation or skip grace endpoints.

The screenshots also expose a real remaining admission boundary: end->isGrace
is rejected by v0.143. It explains spacing changing at a grace stop and returning
at its parent. Pulling back from the original main endpoint reaches before-
graces, and then later after-graces of the source owner, including equal-tick
anchors. v0.144 addresses both the test model and grace-endpoint admission.
Native verification of the corrected transitions remains pending.
