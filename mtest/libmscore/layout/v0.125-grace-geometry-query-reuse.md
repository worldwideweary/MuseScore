# v0.125: share eligibility across one complete geometry query

The user reports v0.124 native mtests passing but held-arrow editing still
feels slow. The new timing log shows progress, not a resolution: median
experimental command 112.419 ms (41 experimental commands), versus 202.424 ms
in the earlier log. Median context count/time drops from 19,950/129.709 ms
to 5,622/34.379 ms; the context counter changed in v0.124 to actual chord
evaluations. The group still incurs 73 merged geometry queries, 105 after
plan implementations, and five system plans per typical step. Median curve
fitting remains about 0.231 ms. Timings are instrumented; operations differ
within each recording and this is not a controlled speed benchmark.

## Implementation

v0.124 created a separate cache per component-extraction or shape-distance
helper. Each helper avoided repeated rectangle-pair scans but rechecked the
same group's chords when the next helper began. Pass the cache through the
complete read-only after/merged packing query. For merged geometry, share it
through packing and the subsequent source, target and grace projections.

The public planner/geometry APIs stay unchanged. Private helpers accept the
optional caller cache; standalone callers still create their own local cache.
Scope comparisons and all predicates remain those of v0.124. Packing and
projection read positions and component shapes but do not change musical
eligibility. The cache cannot escape a public query. Every beam preparation
iteration, later geometry query, and edit starts fresh. Pair policies and
physical rectangles continue to be evaluated on every call.

No curve-fitting, padding, shape, beam-convergence or publication rule is
changed. In particular, the 73 geometry queries are not reduced by this
increment; this removes repeated work inside them. Further gains may require
addressing those repetitions separately after measuring this change.

## Validation

- C++11 syntax checks for gracespacing4.cpp and tst_spacing.cpp.
- Local exact old/new eligibility harness retains agreement in all 43,200
  cases (mock DOM, not native timings).
- Sixteen exact geometry-function mock cases check projection order and
  coordinates, shared cache forwarding, failure paths and atomic outputs.
- Extend native graceContextCachePolicies: a successful complete geometry
  query is followed by an unsupported slur line-type edit, atomic rejection,
  restoration, and identical planned member positions. This checks the cache
  does not survive a query boundary.
- Existing native edited-slur, third-slur, moved-stem, repeated-layout,
  beam-preparation and legacy-style restoration tests remain in place.
