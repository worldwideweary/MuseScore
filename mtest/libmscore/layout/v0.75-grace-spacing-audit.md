# v0.75: grace-note spacing follow-up, initial source audit

User observation: blue-paper Evolution and Studio 4.7.5 render the supplied
acciaccatura group differently. Studio appears to open the last-grace-to-main
note gap and tighten the first sharp-to-flat grace-note gap. Slur placement
also differs. Evidence: image(20261023-103453).png (Evolution) and 103510
(Studio). Exact score/style data was not supplied with this aside; screenshots
alone do not prove which defaults or collision inputs cause each difference.

## Confirmed source boundaries

- Evolution Chord::layoutPitched in chord.cpp places before-grace notes from
  right to left using each chord's _spaceLw/_spaceRw, minNoteDistance and
  graceNoteMag, reserving the result in the main chord's left space. A similar
  loop exists in the TAB layout path. Chord::layout2 repositions after-graces
  using the following segment and existing space values.
- Pinned Studio horizontalspacing-4.7.5.cpp note-padding logic distinguishes
  grace-to-grace, grace-to-main and main-to-grace pairs. graceToGraceNoteDist
  and graceToMainNoteDist impose separate minimum padding after scaling.
  Pinned defaults are 0.3sp and 0.45sp respectively. These values alone do not
  reproduce the full group algorithm or explain every accidental collision.
- Studio ChordLayout::appendGraceNotes attaches before-grace groups to the
  current segment and after-grace groups to a following segment. Its
  repositionGraceNotesAfter explicitly runs after horizontal spacing. The
  equivalent group-layout implementation needs to be retrieved/audited before
  choosing an adapter; it is not present among the current reference files.
- Evolution style.cpp explicitly skips the two Studio grace distance tags
  when reading 4.x files. Do not assume their values are already imported or
  that minNoteDistance is an equivalent user control.
- spacingplan4.cpp rejects chords with graceNotes; spacingcollision4.cpp
  rejects grace chords. The optional full placement plan therefore falls
  back for these inputs. Enabling spacingLayout4 does not presently select
  a Studio grace-group implementation. Removing the guards is insufficient.

## Proposed audit and implementation order

1. Finish the later-system header issue recorded at v0.74.
2. Retrieve the pinned 4.7.5 grace-group layout/collision source and trace its
   call order, scaling, accidental/stem clearances and main-note attachment.
3. Build labeled controls with matched fonts, sizes and explicit styles:
   plain before-graces; sharp/flat/natural groups; both stem directions;
   then after-graces and multiple voices. Use the same originals in both apps.
4. Adapt ordinary before-grace group spacing behind spacingLayout4, preserving
   the legacy-off algorithm. Decide whether to expose separate optional style
   distances only after checking the source defaults and serialization needs.
5. Integrate its full geometry and system-width contribution before admitting
   grace groups to the planner. Test actual application, repeat stability,
   on/off restoration and appropriate unsupported-context rejection.
6. Reassess slurs after horizontal note positions agree. Audit grace slur
   anchors, contour and collision clearance separately; spacing changes alone
   must not be presented as a slur-layout port.

This is an initial audit/checkpoint, not an implementation or a completed
source comparison. No code, score defaults, UI, or test expectations change.
Files changed: this audit and v0.74-spacing-milestone.md. No rebuild is needed.
