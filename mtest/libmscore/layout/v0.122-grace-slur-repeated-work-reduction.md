# v0.122: first grace-slur editing performance increment

## Report and scope

User reports the v0.121 edit no longer jumps, but compares slow experimental
editing with normal editing using normalLayout.mp4 and experimental Layout.mp4.
Both are 60 fps recordings; their durations are 2.4 and 11.366667 seconds,
respectively. They show different musical groups (plain versus altered), so
video duration is not a valid numerical speed ratio. Review frames confirm
slur-grip interaction in each. No native timed profile is available here.

Extra collision computation is expected, but sluggish interaction is not an
intrinsic requirement of the new engraving. Source inspection identifies
avoidable duplicate planning and component extraction in every curve update.
This is a first bounded optimization, not a claim that normal editing speed
has already been restored.

## Reuse validated components within one query

buildGraceMergedSlurObstacles4 already builds complete validated combined
geometry. That geometry contains all target/main and planned grace component
rectangles, with identities. Previously the collector extracted and validated
the physical components of every obstacle chord again.

Reuse the existing geometry.target rectangles. For each accepted member,
subtract its planned origin and add its actual published parent/segment/
measure position. Main components subtract the target chord position instead
of a grace plan offset. Preserve musical member/component order, exclude the
same starting anchor and ledgers, validate finite translated bounds and
publish atomically. The source and full joint geometry are still validated;
no eligibility or collision rules are relaxed. This removes the collector's
second round of native shape resolution and component policy checks.

## Reuse raw anchors supplied by the layout pass

layoutSystem/Slur::layout computes raw SlurPos before calling
SlurSegment::layoutSegment. v0.121 computeBezier then called slurPos again to
avoid using already-fitted grip points during editing. The re-query repeated
full combined geometry validation through the beam-anchor helper.

Record the raw p1/p2 supplied to layoutSegment and use them for repeated curve
computation and direct grip previews in that layout frame. Every new
layoutSegment invocation replaces the two raw points before computing. A new
or cloned segment starts without a valid raw frame and retains the slurPos
fallback if needed. No fitted curve, user offsets or external beam cache is
used as the raw input. This removes one redundant raw-anchor query per normal
modern curve computation while preserving the no-jump automatic base.

The derived raw frame does not serialize. Style, anchor, direction and score
geometry changes go through layoutSegment as before. A regression test moves
the physical measure, supplies fresh raw anchors, verifies all four rendered
points translate, then restores the original frame and verifies the old curve
and note geometry return. Existing direct-preview, grip, segment/object-offset,
repeat-layout, clearance and style-restoration checks remain active.

## Validation and limits

Local checks: C++11 source/test syntax and moc; 70 executions of exact old and
new collector bodies with mocked DOM/component producers, checking equal
outputs and rejection plus zero repeated component extraction in the new
collector; direction/scale/geometry, moved-position and atomic failure cases;
staged whitespace and parent-patch applicability. Full native UI/layout
performance cannot be measured in this environment.

This increment still performs full joint-geometry validation for the remaining
render queries, the same bounded collision fitter, and the general experimental
system-spacing passes. Further profiling/optimization may be needed if the
interaction is still slow. Do not trade away the clearance tests to hide that.

Apply after v0.121 and run tst_spacing/tst_beam. Repeat the same M3 grip movement
in the same score/zoom/build mode for a meaningful interactive comparison.
Report whether the delay is reduced or still substantial. Rendering and
spacing should remain equivalent; no new visual comparison score is needed.

Files: gracespacing4.cpp, slur.cpp/.h, tst_spacing.cpp,
studio-spacing-guide.md and this note. Next verify native correctness and the
interactive result; if still slow, profile remaining joint geometry/spacing
work before making further changes.
