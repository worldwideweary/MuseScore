# v0.124: reuse grace-query chord eligibility

## Evidence from v0.123

The user reports responsive mouse dragging, a small delay after release, and
large accumulated latency when holding an arrow key. The supplied native log
shows repeated experimental commands around 200 ms, versus ordinary commands
around 4-6 ms. The pasted experimental series has median command time
199.941 ms, 19,722 item-context checks taking about 127.947 ms, 73 joint
geometry queries, and five system spacing plans per command. Actual curve
fitting totals about 0.233 ms. These are instrumented, overlapping stage
times, not additive totals or a prediction of uninstrumented performance.

## Change

Separate the unchanged chord-level eligibility predicate from item-level
checks. Introduce SpacingContextCache4 for one read-only component query.
Use it while extracting a grace chord's own components and while computing
the distance between two grace shapes. Reuse successful and rejected chord
eligibility results across note/stem/accidental/ledger component pairs.

The cache records the grace admission flag, scoped main, null/non-null
context, and context root/pair vectors by value. Changing that scope clears
the chord entries. Equivalent temporary merged contexts can reuse entries;
an address-only key would not work because policy wrappers reconstruct them.
includeOwner membership is still checked for each pair before cache lookup.

Every item still checks its own track, staff type and valid chord ownership.
Every pair still checks score and scope membership, geometry-dependent
padding, magnification, kerning and distance. No component rectangles,
pair policies, packing results, anchors, or fitted curves are cached. Stack
locals end before any edits or beam preparation; no state is retained on
the score, chords, or slurs. Uncached public queries keep their behavior.

This increment targets repeated eligibility scans. It does not eliminate
the 73 geometry queries or five system plans, skip command layout, change
undo, or claim that held-arrow editing has already reached native speed.

## Validation

- Local exact-function old/new harness: 43,200 item eligibility comparisons
  agree, across accepted/rejected contexts, scope changes, grace flags,
  articulations, ties/note spanners, slur admission/counts, invalid components,
  rests, and missing ownership. Full spanner-map scans in that mock workload
  drop from 21,120 to 472. This is work-count evidence, not native timing.
- New native graceContextCachePolicies regression compares cached/uncached
  acceptance and exact padding/clearance/kerning, including untouched outputs
  on rejection, repeated calls, invalid components, and switching between
  merged, local-before, ordinary-after, and owner-inclusive scopes.
- Existing complete-plan slur edit, third-slur rejection, geometry, repeat
  layout and style restoration tests now exercise the local reuse.
- C++11 syntax checks pass for both modified production translation units
  and tst_spacing.cpp; moc succeeds. Native layout tests cannot run locally.
